Thread pages

What happens today

One step back, and replies that lose their place

Screenshots of dame.is at 390px wide, taken this afternoon.

  • The page fetches six posts above and draws one. Record.jsx asks the AppView for getPostThread(uri, { depth: 6, parentHeight: 6 }) and then renders <ParentChain parents={parents.slice(0, 1)} />. ParentPostCard already has a “root” tag that can never show, because the slice never lets a second ancestor through.
  • Replies are fetched from the linked post down. Replies to the posts above it are never requested, so which replies you see depends on which post you came in by. splitSelfThread then lifts the continuation out of the tree and pools the replies on every lifted post into one leftover list, which is the pooling in the second screenshot.
  • The whole chain above any post is one request away. The AppView accepts parentHeight up to 1000 (checked today: 1001 is refused). Replies to earlier posts need the thread fetched from its first post as well.

From the Anisota code

Four ideas worth borrowing

Anisota's traditional thread view (TraditionalThreadView.jsx) and threadUtils.js already solve most of this for a client. The parts that carry over to a personal site:

  • Fetch from the root. When the opened post is a reply, Anisota fetches the thread again from record.reply.root.uri, keeps the post you asked for as originalRequestedUri, and scrolls it into view. Every member of a thread then gets the same complete picture.
  • Walk the author's chain to its end. getPostThread has no “truncated” flag, so extendAuthorChain re-fetches from the last post it has, grafts on what comes back, and stops when nothing does (capped at 40 fetches). Dame wrote a ten-post thread on 15 October, which runs past the default depth of six from the root.
  • Group other people's replies into conversations. flattenThread roots each conversation at its highest post not by the author and keeps the exchange together. It sorts conversations by their total likes, which suits a client better than it may suit a personal site.
  • Keep linear runs at one indent. When each reply has exactly one reply, the traditional view renders the run flat (flattenLinearThread) instead of stepping right each time. dame.is caps the stepping at four levels, but a two-person exchange still reads as a staircase.

Option A

The whole thread, opened at your post

Every post in one of Dame's self-threads opens the same page: the thread from post 1, each post at full size, numbered the way the folded feed row numbers them. The post the link named is marked and scrolled into view.

  • aNumbers in the margin. On a desk they hang in the gutter with each post's time beneath, the way the ledger hangs its verbs. Each number links to that post's own URL, so the folded feed row's verse numbers and this page are the same object at two sizes.
  • bThe linked post gets a soft wash that fades after a couple of seconds, and its number stays in the accent. No bar or rail: the feed's hover bar was taken out in #335 and this shouldn't bring one back.
  • cThe trail keeps the post's rkey as its last crumb (as #338 settled) and adds its place in the thread, 3 of 6.
  • dReplies are filed under the post they answer, with the reply counts in each stats line linking down to them. See Replies by post.

Trade-off. Six URLs show one page. That suits a thread that reads as one piece of writing, but the page for post 8 of 10 opens a long way down, and the jump has to happen before the page reveals or it reads as a lurch (and it should not animate under reduced motion). The tab title and the share card can stay per post, so a link to post 3 still previews post 3. The foot's Earlier and Later step around the thread as a whole rather than landing on its own posts.

What it takes

  • When the post is Dame's and record.reply.root is Dame's too, fetch getPostThread(rootUri, { depth: 6, parentHeight: 0 }) instead of fetching from the linked post, and keep the linked URI to mark.
  • Run the existing splitSelfThread from the root, so the chain is 1 to N and the replies are everyone else's, then file those by the post they answer.
  • For a chain longer than seven, probe the tail as Anisota's extendAuthorChain does. A branched thread (two self-replies on one post) stops at the branch, as splitSelfThread already decides.
  • Scroll to [data-at-uri] of the linked post before the reveal; the wash is a CSS animation on that one element.

Option B

Fold the thread above the post

The linked post stays the first full-size thing on its page. Above it, every post before it in the thread, set as quoted context the way the one parent is set today. Past two, the middle folds into a line that opens in place.

  • aEvery post above is drawn, numbered from the thread's first post, in the quoted voice ParentPostCard already uses. Times replace “16m ago” because in a thread the spacing between posts is the interesting part.
  • bThe fold appears only when it would hide two or more posts (hiding one saves nothing). It's a <details> that opens in place.
  • cBelow the post nothing changes: the continuation and the replies are drawn as they are now.

Trade-off. The cheapest change by far: the posts above are already on the page for threads up to seven long. But the thread reads in two voices, small and indented above the post and full size below it, and replies to the earlier posts are still missing. It fixes the first screenshot and not the second.

What it takes

  • Drop .slice(0, 1) from the ParentChain call in Record.jsx, and raise parentHeight (it accepts up to 1000).
  • Number the ancestors from the root when the root is Dame's; for anyone else's thread, see option D.
  • Add the fold to ParentChain: first, then a summary line, then the last.

Option C

Contents in the margin

Each post keeps its own page, alone. The thread becomes something to move through: a contents list in the empty right margin on a desk, a strip under the trail on a phone with the list in a sheet, and previous and next post in the thread at the foot.

  • aThe contents list gives each post's number, first words and time, and its reply count. It stays in view as you scroll.
  • bOn a phone, “‹ 2” and “4 ›” step through the thread; the middle opens the list in a sheet.
  • cPrevious and next in the thread sit right under the post, ahead of replies. The foot's Earlier and Later then step over the thread as a whole, since otherwise they would name the same two posts again.
  • dRead it whole opens option A's view of the thread, if both are built.

Trade-off. Suits long threads, where one page would be a lot of scrolling, and keeps each post the clear subject of its URL. Reading the thread straight through becomes six page loads, though, and the phone gets one more band of chrome. It works best as a companion to A rather than instead of it.

What it takes

  • The same root fetch as A; the list needs only the chain, so parentHeight: 1000 plus the existing descendants would also do.
  • Desk: a sticky aside in the record page's right column. Phone: the strip below the trail, and the list in BottomSheet.
  • Number links reuse recordPathFromAtUri, as the ledger's verse numbers do.

Option D

Conversation context for replies to other people

When Dame's post answers somebody else, the context above it is other people's words, and usually a lot of them. Show where the conversation began and the two posts just before Dame's, fold the middle, and say who is in the fold.

  • aThe conversation's first post always shows: it says what everyone is talking about. Its picture stays a thumbnail.
  • bThe fold names who is in it and opens in place. Here it hides seven posts, one of them Dame's.
  • cThe two posts nearest Dame's always show, on one rail with avatars, since several people are speaking. Dame's own thread context (A, B) needs no avatars because it is one voice.
  • dReplies below: a run where each post has one reply stays at one indent, and consecutive posts by one person share a byline. Poe's six-level staircase in the third screenshot becomes three blocks.

Trade-off. How much to fold is a judgement call; some readers want the whole exchange, and the fold costs them one tap. The mixed case needs a rule as well: a self-thread that answers someone else (or Dame's reply to a commenter inside Dame's own thread) would get D's context above, then A's numbered posts.

What it takes

  • parentHeight: 1000 on the request the page already makes returns the whole chain; no second request.
  • Show the root and the last two, fold the rest when that hides two or more. Fold labels list distinct handles in order of first appearance.
  • Flatten linear runs and merge same-author neighbours in Comments.jsx; both are pure functions over the thread view and easy to test.

Whichever option

Replies filed by the post they answer

Once a page shows more than one of Dame's posts, every reply should say which post it answers. Two ways to file them.

Trade-off. Collected at the end keeps the thread uninterrupted and is closest to today's page. In place keeps each conversation beside its post, but a thread with replies opened reads in fits and starts. In both, a back-and-forth between two people keeps one indent. Order within a group could stay by time, as the site does now; Anisota sorts conversations by total likes instead, which is a choice about what the page is for.

Where I'd start

A for Dame's own threads and D for replies to other people, with replies filed by post and collected at the end. They cover all three screenshots and share one fetch path (from the root). B is a reasonable first step if you want something live soon: it is a small change to code that already fetches what it needs, and nothing in it has to be undone to build A later. C is worth adding once threads regularly run past eight or ten posts; the longest self-thread since 8 October ran ten.

I haven't prototyped any of this in the app, so the scroll-on-load in A and the sticky aside in C are untested against the site's chrome, which already has its own sticky bars.

Open questions

  1. Should a link to post 3 open scrolled to post 3 (as drawn in A) or at the top of the thread with post 3 marked?
  2. Should a shared link to any post in a thread preview that post, or the thread's first post?
  3. Replies to earlier posts: on every member's page, or only the replies from the linked post down?
  4. Reply order within a group: by time, or Anisota's most-liked first?

Also noticed. Post 3's text ends in U+FFFC, the object replacement character some iOS text fields leave behind. The site draws it as a boxed “OBJ” glyph (visible at the end of the post in the first screenshot). renderPostText could drop it.
