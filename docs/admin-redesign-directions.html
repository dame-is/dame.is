The read

What's in the way today

The admin works — it's the navigation and the density that cost you time. Six things showed up repeatedly while reading through it.

  1. Everything is one route

    Thirteen if (view === …) branches return whole different pages from a single component. There's no shell that persists, so every surface is a full repaint.

    src/pages/Admin.jsx:82–145

  2. The menu is a wall of prose

    Each of the sixteen entries carries a paragraph of explanation. Nothing to scan by — no counts, no recency, no sense of which surface actually needs you.

    PICKER_GROUPS — Admin.jsx:218

  3. Back is the only navigation

    Every list and editor offers ← All collections or ← Back to list. Blogging to Logging is three screens with a menu in the middle.

    Admin.jsx:566, 964, 1466

  4. Save isn't on the page

    The editor passes hideActions and pushes Save, Delete and Close into the floating bottom chrome bar. The page's primary action lives outside the page.

    RecordEditorPage — Admin.jsx:1437–1483

  5. Lists can't be searched

    RecordList gives you select-mode and Load more. That's it. Finding one play among thousands of fm.teal.alpha.feed.play records means paging by hand.

    RecordList — Admin.jsx:405

  6. Mobile is the desktop, narrower

    The only phone-width rule drops the page padding. The toolbar wraps, the rkey/preview/timestamp row squeezes to nothing, and no control is near a thumb.

    src/styles/app.css:313–319

Direction one

Console

Software you keep open

A rail that never goes away. Every surface is one click from every other surface, and the count next to each one tells you what's in there.

  • Persistent left rail, grouped Content / Site / Studios, with a live record count per collection.
  • Search across every collection from the rail — or ⌘K from anywhere.
  • Lists become tables: state, title, publication, date, sortable, with a filter row above.
  • Editor gets a meta sidebar — status, publication, slug, at-uri, raw JSON, delete — so Save can sit in the page header where you'd look for it.
  • Build — largest of the four. New shell, nav config, per-collection counts, a search index, and every studio re-parented into the shell.

The tradeoff. Console is the most conventional and the most legible — anyone who has used a CMS knows it on sight. It is also the direction that looks least like dame.is: the rail is furniture the rest of the site doesn't have, and it eats 238px that the phone can't spare, which is why mobile has to translate it into a tab bar rather than shrink it.

Direction two

Ledger

The book the site is written in

No rail, no menu, no chrome. One ruled column showing every record in the repo at once, and a command line at the top that filters, jumps and creates.

  • Collections stop being places. One stream, one rule per row, the NSID as a column you can filter on.
  • The command line replaces navigation — type to filter, >blog to scope, n for new, g s to jump to the sky studio.
  • Records open in place, expanding into a ruled form where every field keeps the same gutter as the list.
  • Grouped by day, newest first, so the admin reads like the site's own feed.
  • Build — moderate. The list and editor are genuinely simpler than what's there now; the work is the command parser and a cross-collection fetch.

The tradeoff. This is by far the most dame.is of the four — it's the same ledger language the feed and the x-ray rows already speak, and it's the only direction where the phone layout is the desktop layout rather than a translation of it. The cost is that the nine bespoke studios (Sky, Ratioed, Resume, Nav, Publications) don't fit a ledger row; they'd have to stay as full-page escapes reached by a g command.

Direction three

Workbench

Never lose your place

Three panes: surfaces, records, editor. Selecting a record fills the right pane instead of navigating away, so the list you were scanning is still there when you're done.

  • Nothing is a page load. Edit ten records in a row without a single back-button trip.
  • Live preview as a pane tab — Edit / Preview / JSON — showing the post as the site will actually render it.
  • Unsaved state is always visible in a status strip under the editor, so you can leave a record half-written and know it.
  • The icon rail stays narrow (78px), giving the list and editor the room the current single column wastes.
  • Build — moderate-to-large. The panes are straightforward; the real work is lifting editor state out of the route so selection doesn't remount, plus a preview renderer.

The tradeoff. Workbench is the biggest quality-of-life gain per screen — editing several records in a row stops being a chore. But three panes need roughly 1100px to breathe, so the phone gets a genuinely different layout (a drill-down stack) rather than a compressed one, which means two layouts to maintain rather than one.

Direction four

Front desk

Know the state of the site

The root of the admin stops being a menu and becomes a report: what's published, what's stalled, who signed the guestbook, what you were last working on. The lists come after.

  • Status before navigation. Four counts across the top, with anything needing attention carrying a rust border rather than a badge.
  • “Needs you” is a real list — stale drafts, unmoderated signatures, a piece waiting to be sealed — each with the action attached.
  • “Pick back up” remembers the last four records you touched, across every collection.
  • The editor goes the other way: one centred measure, nothing in the margins, meta folded into a Details disclosure under the body.
  • Build — small-to-moderate for the dashboard (it's counts and a recents list); the surface grid can reuse the current picker groups almost as they are.

The tradeoff. Front desk is the only direction that tells you something you don't already know when you open it, and it's the easiest of the four to ship — but it doesn't fix the navigation underneath. Behind the dashboard, moving between surfaces is still list → back → list unless you pair it with one of the other three.

If it were mine to pick

Front desk as the root, Workbench underneath

They solve different halves of the problem and stack cleanly. Front desk fixes the opening screen, which is the one that's actively unhelpful today — sixteen paragraphs of description and no state. Workbench fixes the middle of the job, where you're editing four records in a row and paying a full page load between each.

Ship them in that order: the dashboard first, since it's mostly counting records you already fetch and needs no structural change; then the three-pane workbench behind it, which does need editor state lifted out of the route. Ledger's tally strip and its g-command jumps are worth stealing into either one.

The honest case against: Ledger is the direction most obviously of this site, and if the admin is only ever used by one person who knows every collection by name, the ledger's command line beats any amount of navigation furniture. It's the riskiest pick and the most characterful one.
